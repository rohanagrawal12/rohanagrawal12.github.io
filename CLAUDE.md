# Bulletin: notes for Claude

Bulletin ("Find your thing.") is a student opportunity finder. A student writes a few sentences about themselves in a short quiz, and the app ranks clubs, volunteering and programs with a 1-10 match level. It starts with The Village School in Houston, TX (98 school clubs), plus 31 Houston community opportunities and 28 national or online "Explore" programs.

## How to work with the owner
- The owner is new to coding and often works from a phone. Give short, plain-English steps with the exact button names, one thing at a time. Say plainly when something could not be checked.
- They dislike anything that looks "AI-made" or busy. Keep the design clean and simple: black, white and gray with one red accent, lots of empty space, square-ish corners, no gradients, glows or emoji.
- They want changes live quickly. Pushing to `main` updates the website, so keep commits small and say what changed.
- Never put secret keys in this repo. The Supabase publishable (anon) key is public by design and is fine. The Supabase secret or service_role key is never OK.

## How the app works
- One state object `S` is saved in the browser under `localStorage` key `bl.state`. `bl.users` holds a device copy of each account (for online accounts: name, role, provider, org, friends and `sb:1`, never a password or quiz answers), `bl.msgs` the messages, `bl.custom` provider posts and `bl.sb` the online login. Settings > clear removes them all.
- **Accounts and saving online (Supabase).** The block that starts `/* ---------- accounts and saving online` holds `SB_URL` and `SB_KEY` (the publishable key, public by design). If either is empty, `SBON` is false and the whole site is device-only like before (accounts with SHA-256 password hashes in `bl.users`). With them set, guests never touch the network (the one exception is the school waitlist form, below). Sign-up (`dosignup`, `/auth/v1/signup`) and login (`dologin`, `/auth/v1/token?grant_type=password`) go through `sbRaw`; data calls (`/rest/v1/...`) go through `sbReq`. The key is sent in the `apikey` header only, never as a Bearer token (the publishable key is not a JWT); the person's access token goes in `Authorization: Bearer`. `sbReq` refreshes the token when it is about to expire (`sbToken` and `sbRefresh`: one shared refresh, and it re-reads `bl.sb` first in case another tab refreshed) and retries once on a 401. If the refresh token is refused the login is over (`sbEnded`: wipes the personal data from the device and shows the log in screen with a notice). The login lives in `bl.sb` = `{uid,email,access,refresh,exp,known:{saved,doing},dirty,meta,adm}` (`SBS` in memory). After login or sign-up, and on every page load while logged in, `sbPull` reads `profiles` (name, role, is_provider, org, quiz_answers) and `activity` (opp_id, kind saved or doing) and merges: what is online, plus what was added here since the last sync, minus what was removed here (`known` is what the server had at the last sync). Online quiz answers win unless `dirty` (the quiz was finished here and not sent yet). A missing profile row is created from the sign-up details (`meta`). `sbFlush` then sends the differences (upserts with `Prefer: resolution=merge-duplicates`, and deletes). `sbQueue` runs it 600 ms after a save, doing or quiz finish. Failures retry with a growing delay (up to 5 times) and again on the browser `online` event or when the tab becomes visible, so offline changes are kept and sent later. Log out and Settings > Clear data (`sbOut` and `sbWipe`) remove the quiz answers and saved and doing items from the device (they stay in the account), so the next person on a shared computer does not see them. In online mode an old device-only login (`S.me` without a matching `bl.sb`) is dropped at boot. Delete my account calls the database function `delete_my_account()`; if it is missing (404 / PGRST202) it deletes the profile and activity rows, logs out and says the login itself is not removed yet. Friends, messages and provider posts are still device-only. Form helpers: `authMsg` (shows an error in place, above the button, so typed text stays), `authBusy` (disables the button while working), `FORM` (name and email carried between log in and sign up, memory only), `INFO` (a notice on the auth screens and Settings, memory only, cleared by the next action, tab click or Back) and `privNote()` (the honest note about where quiz answers are kept).
- `S.stage` goes intro (3 welcome slides: Home with the video box, About us, Get started) > auth > prompt > quiz (4 pages, defined in `PAGES`) > loading > app. Tabs: School, Community, Explore, My Activities, plus Search and Settings.
- **Sign up button in the top bar.** Guests (nobody logged in) see a white "Sign up" button (`#hacct`, class `.ha`) in the header, right before the sun-shaped Settings button. `render()` sets `$("hacct").hidden=!!u`, so it disappears after sign-up or log in and comes back after log out. It runs `act("signup")`, which opens the Create account form (that form has an "Have an account? Log in" link). Header layout: `#nav{flex:1 0 auto}` keeps the tabs from sliding under the search box, and between 761px and 950px the search box drops to its own row. `test_sb.py` section S15 checks that nothing in the header overlaps at 320, 390, 800 and 1440px.
- **Change password** (Settings > Account, online accounts only: `sbIn()`). The button runs `act("chpw")`, which opens the full-screen stage `chpw` (`pwView()`, built like the log in form, so the browser Back button and the ‹ Back link work). `dochpw` needs 6+ characters and two matching boxes, then calls `sbReq("/auth/v1/user",{method:"PUT",body:{password}})`, the same call supabase-js makes for `updateUser`. It does not ask for the old password, because the person is already logged in. Messages: `same_password`, `reauthentication_needed` (only if Supabase's "Secure password change" is on and the login is over 24 hours old: it says to log out and log in again) and the server's own text for `weak_password`. On success `PWOK` swaps the form for a "Password changed" panel with a Done button (`back2`). `showpw` flips both boxes between hidden and shown without re-rendering, so typed text stays. A hidden `autocomplete="username"` field holds the email so password managers update the right login. `fixStage()` and `render()` turn a leftover `chpw` stage with no login into `app`, and `sbEnded` sends it to the log in screen. `fake_sb.py` answers `PUT /auth/v1/user` (flags `reauth`, `min_pw`, `force401`; list `pw_changes`) and `test_sb.py` section S17 covers it. The owner changed a password on the live site on 2026-11-20 and said it worked (told to Claude in chat), so the real project accepts `PUT /auth/v1/user`.
- **School waitlist.** Full-screen stage `waitlist` (`wlView()`, built like the log in form, so the ‹ Back link and the browser Back button work). It opens from Get started > the Schools and organizations row > "Join the waitlist →" (`.wl2`) and from Settings > More > School waitlist (`act("waitlist")`; both only when `SBON`, and `fixStage` turns a leftover `waitlist` stage into app or intro in device-only mode). `dowl` trims and checks (organization 2+ characters, email shape, at most 254) with plain messages, then calls `/rest/v1/rpc/join_waitlist` through `sbRaw` with `{p_org,p_email,p_note}` and the publishable key only: never an `Authorization` header, even for a logged-in person (the function is open to `anon`; `fake_sb.py` records a violation otherwise). A hidden trap box (`#w_hp`, class `.hp`) that a robot fills makes the page pretend success and send nothing. Typed text lives in `WLF` so a redraw keeps it; `WLOK` holds the email for the thank-you panel. Nothing about an entry is stored in the browser. Errors go through `wlErr` (404 / PGRST202 means `supabase/admin.sql` has not been run: "The waitlist isn’t open yet.").
- **Admin page.** `supabase/admin.sql` makes `waitlist`, `admins`, `join_waitlist()`, `is_admin()` and `admin_overview()`. The two tables have no rights for `anon` or `authenticated` (row-level security is on as a backstop) and the three functions are SECURITY DEFINER with `search_path=''`. `join_waitlist` (anon and authenticated) trims and validates, keeps one row per lower-cased email, returns success without writing when the email is already listed (so it cannot be used to look people up) and refuses new rows at 30 a minute or 10,000 in total. `is_admin()` and `admin_overview()` (authenticated only) check the `admins` list, which only the SQL Editor can change (a row goes with its account). `admin_overview()` returns jsonb: counts (accounts, accounts in 7 days, quiz finished, providers, saved, doing, waitlist), a 14-day sign-up chart in Houston time, top saved (8), schools (6), grades (9), the newest 500 accounts (`accounts_list`: name, email, role, provider, joined, last log in, quiz done, and the school typed if that email is on the waitlist; added 2026-11-21 because the owner asked to see who signed up) and the newest 500 waitlist rows (each with `has_account`); it raises 42501 "Admins only." for anyone else and never returns anyone’s quiz answers, saved items or password hash. In the page: `sbAdminCheck()` (`is_admin`, run by `sbSync` and after log in) only sets a hint, `SBS.adm` (kept in `bl.sb.adm`); `admLoad()` calls `admin_overview` and the database re-checks every time (403 / 42501 sets `SBS.adm=false` and `render()` sends the person back to School; 404 / PGRST202 sets `ADMNO` so the page stops asking). `sbAdmin()` is the page’s yes or no. An admin who logs in lands on `S.tab="Admin"` (`dologin`); the header Admin button (`#hadm`, `data-tab="Admin"`) shows for admins only; `render()` forces anyone else’s `S.tab="Admin"` back to School. `adminView()` shows six number tiles, the waitlist (Copy emails, and Copy as spreadsheet through `csvSafe`, which puts a `'` before any cell starting `= + - @` so a spreadsheet will not run it as a formula; entries whose email has an account get a "Has an account" tag), Accounts (name, email, role, joined, last log in, quiz done, and an "On the waitlist: school" tag; the first 10, then Show more adds 20 through `ADMLIM` and `act("admmore")`; if the project still has the older `admin_overview()` with no `accounts_list`, the panel says names and emails are not turned on yet and the rest of the page works), the 14-day bars, Most saved, Schools and Grades. `ADM` lives in memory only and `sbWipe` clears it, and `ADMLIM` (log out, `sbEnded`, a new person). Everything that visitors typed (waitlist entries, account names and emails) is escaped with `esc()`. Confirm email is off, so anyone can register any address: the owner must log in once with their own email and password before running section 3 of `admin.sql`, so the account that becomes admin is really theirs.
- Pages are string templates. `render()` rebuilds the page. All clicks go through `act(name, data)` using `data-act` attributes, and `go(tab)` switches tabs.
- Matching is `score()`. It stems the student's answers and expands them with a small synonym list, compares them to each opportunity's tags (heaviest), name, category, "good fit" traits and description with rarity weights, adds bonuses for the "want" and "why" picks and skill ratings, subtracts for "avoid" text, applies filters (grade, hours, format, ride, paid, free time, closed), then scales each tab to 1-10.
- Themes: auto, light, dark, forest, yellow, marker (`THEMES`). Brand name is `BRAND`.
- `const VIDEO` near the top fills the video box on the first welcome screen. It is set to the owner's Synthesia share link (`https://share.synthesia.io/7f128605-78cd-5867-8b47-7f6732abaf0f`, "Bulletin: Find your thing explainer", 1:19, 16:9, made on the free plan so Synthesia's watermark shows in the player). The box always shows the thumbnail (`THUMB`, `assets/video-thumbnail.png`). Empty: label "Coming soon", nothing to click. A YouTube or Vimeo link, a Synthesia share link (`https://share.synthesia.io/<id>`) or embed link (`https://share.synthesia.io/embeds/videos/<id>`), an MP4 link or a file path such as `assets/explainer.mp4`: label "Play the video", and clicking the thumbnail swaps in the player (`playVideo()`: an iframe with `autoplay=1`, or a `<video autoplay>`), so it plays on that click. `vidSrc()` works out which kind the link is. A Synthesia share link and its embed address use the same video id (Synthesia's own oEmbed answer for this video shows it), so the owner never needs the embed code. Any other link shows the thumbnail as a "Watch the video" link that opens in a new tab. Checked on the live page in the Claude desktop app's built-in browser (Chromium): one click on the thumbnail starts the Synthesia player in place and the video plays. The owner said on 2026-11-20 that the video plays and the welcome screens work on their iPhone in Safari; Android is not tested.
- Welcome screens (the landing page) are written to the owner's class checklist (Swancoat 6.2.6 Website Checklist: logo, promo message, tagline, first paragraph, clear call to action, About Us story, video, store). Screen 1 "Home": logo, "Find your thing." headline, promo paragraph, the video box, a Take the quiz button and a three-points line. Screen 2 "About us": the startup story, mission and who it is for. Screen 3 "Get started" (stands in for the checklist's store, because the app is free): live counts from `DATA`, three steps, a plan card (Students FREE, Schools and organizations COMING SOON) and a second Take the quiz button. They are the `SL` array (`[caption, headline, paragraph, small text, colour class, art, extra html]`), with helpers `slRd`, `slCta` and `slN`, drawn by `slideView()`. The copy is also in `docs/landing-copy.md`; keep the two in sync. There is no email waitlist box yet (no backend or contact address).
- Welcome screens: `init()` shows them first on every fresh visit (new tab or browser session, tracked by `sessionStorage` key `bl.visit`), even for returning users, unless the site is installed on the home screen. Returning users (`S.seen`) get an "Open the app" button instead of "Log in". Settings > Welcome screens replays them.
- Back button: `hSync()` (end of `render()`) pushes a browser history entry whenever stage, welcome slide, quiz step, tab, My Activities section or compose changes. The `popstate` handler restores that view, the list length and the scroll position. The loading screen is never put in history. In-app Back buttons call `goBack()`, which uses `history.back()` when there is an earlier entry. When adding a new screen, make it change one of those fields so the browser Back button reaches it.
- Lists show 8 items first (`S.lim`). Show more adds `MORE` (20).
- **Take the quiz banner.** While `S.done` is false, `listView()` starts with `quizBanner()` (class `.qb`: a bordered box with a heavy left edge, one line of explanation and a filled Take the quiz button, the first thing on School, Community and Explore). The owner asked for it on 2026-11-21 after making a new account and not finding the small toolbar button. A top-bar button was not used because the phone header is already full (logo, Sign up, Settings). Without the quiz the subtitle says "Not sorted for you yet." and the toolbar has no quiz button; with it done the toolbar shows "Retake quiz" and there is no banner. It is not on My Activities or Search; Settings keeps its own Take the quiz button. Tests: `test_sb.py` S21.

To start a test page in a chosen state, seed it before the page loads, for example an init script that runs:
`localStorage.setItem('bl.state', JSON.stringify({stage:'app',tab:'School',seen:true,done:true,theme:'light',ans:{grade:'10th grade',school:'The Village School',learn:'biology and chemistry',want:['Join a club'],why:['Trying new things'],time:'3-5 hours'}}))`
Also run `sessionStorage.setItem('bl.visit','1')` in the init script, otherwise the welcome screens show first. For a logged-in start, also seed `bl.sb` (see `sb_seed` in `fake_sb.py`) and answer the Supabase address with `fake_sb.py` through `ctx.route`. For Back button checks use `page.go_back()` and read `S.stage`, `S.tab` and `S.step`. Only Chromium is installed in the workspace.
